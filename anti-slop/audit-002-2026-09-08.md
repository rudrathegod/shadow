## Findings

### 1. [HIGH] [FIXED] Overstated invisibility claim contradicts its own hedge and CLAUDE.md — R-36/R-38
`README.md:34` (vs. the hedge at `README.md:16`, vs. `CLAUDE.md`'s "Invisibility" section)

README.md:34 states shadow "stays **invisible in screen shares**" as a flat claim. 18 lines earlier the same README already hedges: "best-effort, not guaranteed... Apple can let modern capture tools see it anyway." CLAUDE.md is explicit: *"Best-effort... don't strengthen the claim in user-facing copy."* Line 34 does exactly what CLAUDE.md says not to do, next to its own correction.

Fix: reword line 34 to match the hedge already on line 16 (e.g. "designed to stay out of most screen shares" rather than "stays invisible").

### 2. [HIGH] [FIXED] Em dash (—) used as default punctuation across nearly every user-facing string — R-02
Dense and consistent, not isolated — this is the largest and most systemic finding:

- `renderer/index.html:29` — `aria-label="Panic — collapse shadow"`
- `renderer/renderer.js:589,593,603,608` — update-button status text: "Download opened in your browser — unzip and replace shadow", "Install failed — click to try again", "Update available: v... — click to install", "Check failed — try again"
- `renderer/renderer.js:682,687,695,700,706,713` — onboarding step copy shown to every new user, six separate em dashes across the six steps
- `renderer/renderer.js:759-760` — Panic button tooltip: "Panic — collapse shadow (... toggles it)"
- `main.js:193,203,206,247,276,307,317,323,377,447,479,485,497` — nearly every status/error string sent to the renderer's visible status bar (`send('status', ...)`, `send('llm:error', ...)`) uses an em dash; this is the single largest concentration in the codebase
- `package.json:4` — description field
- `README.md:42,66,86,212` — "Option A — Download the app", "Option B — Run from source", "First launch — the 1-minute setup", "All Rights Reserved — see [LICENSE]"

Fix: mechanical find-and-replace to comma/period/colon per file, per R-02. Given the volume, this is worth doing as one pass across all listed files rather than spot-fixing.

### 3. [HIGH] [FIXED] Focus ring fails the 3:1 UI-component contrast minimum — R-32/R-34
`renderer/styles.css:9`

`button:focus-visible,input:focus-visible,textarea:focus-visible { outline:0; box-shadow:0 0 0 3px color-mix(in srgb, var(--accent) 34%, transparent); }` — computed ring-vs-background contrast is **2.54:1 on the panel (#121212)** and **2.55:1 on the settings surface (#18181b)**, both below the 3:1 minimum for non-text UI indicators. A keyboard user gets a barely-visible focus ring on both surfaces the app actually uses.

Fix: raise the mix percentage or use a higher-contrast ring color (the neon-green accent at higher opacity, or a light ring, would clear 3:1 easily against these dark backgrounds).

### 4. [HIGH] [FIXED] Onboarding modal has no Escape handler — R-26/R-32
`renderer/renderer.js:674-737` (onboard-scrim)

The settings scrim closes on Escape (renderer.js:659-660 handles it). The onboarding modal has no equivalent handler anywhere in the file — a keyboard user can only exit onboarding via Tab-to-button, not the Escape shortcut every other modal in the app supports.

Fix: add the same Escape handler used for settings-scrim to onboard-scrim.

### 5. [HIGH] [FIXED] Neither modal traps focus or hides the underlying panel — R-32
`renderer/index.html` (#settings-scrim, #onboard-scrim), `renderer/renderer.js`

Neither modal sets `aria-hidden`/`inert` on `#app`, and there's no focus trap or `role="dialog"`. While a scrim is open, Tab still cycles through the main panel's toolbar/composer/action buttons underneath it, so keyboard focus order doesn't match what's visually/logically in scope.

Fix: set `inert` (or `aria-hidden="true"`) on `#app` while a scrim is open, and trap Tab within the open modal.

### 6. [HIGH] [FIXED] Leftover tool-call artifact committed into README.md
`README.md:213-214`

The file literally ends with `</content>` / `</invoke>` — leftover XML from a tool call, accidentally committed into the shipped README. Not in the antislop rule taxonomy, but it's broken, visible garbage in a real user-facing file.

Fix: delete those two lines.

### 7. [MEDIUM] [FIXED: documented reason instead of a forced font swap] Monospace font applied globally, not scoped to code — R-06
`renderer/styles.css:5,8`

`--font` (JetBrains Mono / Berkeley Mono / SF Mono stack) is set on `html,body`, so the panel heading ("Private context, on demand"), chat prose, and every UI label render in monospace — not just `.ai-text pre`/`code`, which legitimately want it. JetBrains Mono is named directly in the skill's "default roster" as a tell when used as the whole-UI aesthetic with no stated reason. Nothing in CLAUDE.md or nearby comments states why prose (not code) is monospace.

Fix: either write down the identity reason ("shadow reads as a dev tool end to end") in CLAUDE.md/DESIGN.md, or scope `--mono` to code blocks only and give body text and headings a proportional font.

### 8. [LOW] [FIXED] Dead icon wiring — icons render but are hidden by CSS
`renderer/styles.css:34,95`; `renderer/renderer.js:11-15`

`.act .ic { display:none; }` and `#smart-toggle .ic, #more-btn svg { display:none; }` are never overridden anywhere later in the cascade, yet renderer.js still injects SVG markup (sparkles, wand-sparkles, message-circle, refresh-cw, zap) into those spans on every load. None of it is ever visible. Distinct from audit-001's icon-choice finding: even a correct glyph choice here would still never render.

Fix: either restore `display` for `.ic` where icons are meant to show, or delete the now-pointless icon-injection code in renderer.js.

### 9. [LOW] [FIXED] Second, independent instance of the generic "sparkles" icon — R-04
`renderer/renderer.js:680,719`; `renderer/icons.js:5`

The onboarding walkthrough's first step also uses `icon: 'sparkles'` (`#ob-icon`), the same generic AI-orb glyph flagged on the Assist button in audit-001. Fixing the Assist button alone won't catch this one — it's a separate call site.

### 10. [LOW] [FIXED: bumped to 30px] Small click targets — R-03 reference only
`renderer/styles.css:19,37,62,139`

`.tb-stop`/`.tb-panic`/`.tb-transcript` (29px, shrinking to 27px in one theme variant) and `#send-btn`/`.more-btn` (30px/28px, down to 26px in one variant) sit below the skill's 44px touch-target reference. This is a desktop mouse/trackpad app, not a touch surface, so this is a minor usability note, not a hard defect.

### 11. [LOW] [NOT A BUG: confirmed main.js enforces minWidth 420, below the danger zone never reachable] Narrow-window reflow risk
`renderer/styles.css:24,51,41`

`#panel-wrap` width is `min(650-660px, 94vw)` with limited reflow below 560px (only a few labels get hidden at that breakpoint). `.s-field span` has a fixed `width:78px` inside a flex row. If the window can be resized below ~400px, the composer row and settings field labels could collide rather than reflow — not confirmed from CSS alone since it depends on whether main.js enforces a window minimum width.
